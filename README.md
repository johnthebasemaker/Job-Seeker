# Job Seeker

Find matching jobs, tailor the resume with AI, and apply without handing your
Indeed password to a robot. Runs entirely on free tiers: Streamlit Community
Cloud, Supabase, GitHub Actions, and free job-search and LLM APIs.

```
Streamlit Cloud (Google sign-in)        GitHub Actions (daily cron)
  profile, discovery, tailoring,  <-->  fetch jobs from APIs, score, dedupe
  ATS report, PDF/Word download             |
            |                               v
            |  apply pack (.json)   Supabase (Postgres + file storage)
            v
Chrome helper on the laptop            Apps Script in the user's Google account
  fills the form, person submits         Gmail invite -> Calendar + reminder
```

## The one design decision everything else follows from

The app never tries to beat Indeed's bot protection. No stealth browsers, no
proxy rotation, no CAPTCHA solving. That would break Indeed's terms, get the
user's account banned, cost money, and fail anyway from a datacenter IP.

Instead: **the app prepares, the person submits.** It finds the job, tailors
the resume, drafts the screening answers, and a browser helper fills the form
in the user's own signed-in browser. They review and click Submit. A CAPTCHA,
if one appears, is solved by the human it was designed for.

Job listings come from job-search APIs (JSearch, Adzuna, Jooble) and company
boards (Greenhouse, Lever, Ashby), not from scraping.

## What works today

- **Profile** - upload a PDF resume, it is parsed into editable markdown;
  contact details, search preferences and a reusable screening-answer bank.
- **Discovery** - fan-out across every configured source, deduped, scored
  0-100 against the profile, every listing labelled with where it came from.
- **Skill advice** - "learn Kubernetes and 7 more of these jobs open up",
  counted from the actual results, with free courses attached.
- **Tailoring** - deterministic ATS report (keyword coverage, structure
  checks), AI suggestions you apply one at a time, a chat editor, and a
  fabrication check that flags anything the AI added.
- **Downloads** - ATS-safe PDF (Typst) and Word (python-docx), single column,
  real text, no tables.
- **Applying** - the apply pack plus a Chrome helper that fills Indeed,
  Greenhouse, Lever and Ashby forms and attaches the right PDF, then stops so
  the person can check it and submit. See `extension/README.md`.
- **Interview invites** - a Google Apps Script that runs in the job seeker's
  own Google account, spots confirmed interviews in Gmail and puts them on
  Calendar with reminders. See `apps-script/README.md`.

## Privacy model

Resumes are personal data, so:

- Name, email, phone, links and postcode are stripped out **before** any text
  reaches the LLM and put back afterwards (`core/privacy.py`). The model sees
  the shape of the career, not who it belongs to.
- Contact details live in `profile.contact` and are merged back in only when
  a PDF or Word file is built (`core/render.py`).
- The default provider is Groq, whose terms say API inputs and outputs are
  not used to train models. **Turn on Zero Data Retention** in the Groq
  console under Settings -> Data Controls before you let anyone else in.
- Every stored row and file can be erased from Settings -> Delete everything.
- Scores, coverage percentages and skill gaps are computed in Python, never
  generated by a model, so no number in the UI is invented.

## Setup

### 1. Supabase (done for this project)

Project `job-seeker`, region `ap-south-1` (Mumbai), free tier. The schema in
`supabase/schema.sql` is already applied: tables, RLS lockdown, the two
private storage buckets and `delete_user_data()`.

You need one secret from the dashboard: **Project Settings -> API -> service
role key**. The app uses it server-side and scopes every query by user id in
`core/db.py`; RLS is on with no policies, so a leaked publishable key reads
nothing.

### 2. API keys (you hold all of them - your friend never needs one)

| Key | Where | Free tier |
| --- | --- | --- |
| `GROQ_API_KEY` | console.groq.com | generous rate limits, no training on your data |
| `JSEARCH_API_KEY` | rapidapi.com, JSearch - open the API page and **Subscribe** to the free Basic plan, a key alone is not enough | a few hundred calls a month - the main Indeed source |
| `ADZUNA_APP_ID` / `_KEY` | developer.adzuna.com | India, UK, Singapore and more; no Gulf coverage |
| `JOOBLE_API_KEY` | jooble.org/api/about | covers India and the Gulf |

Any of them can be left out; the app uses what it has and says so in Settings.

### 3. Google sign-in

Create an OAuth client (type: Web application) at console.cloud.google.com.
Add both redirect URIs:

```
http://localhost:8501/oauth2callback
https://YOUR-APP.streamlit.app/oauth2callback
```

Only basic sign-in scopes are used, so no Google verification is needed.
Put the client id and secret in the `[auth]` block of your secrets, and list
who may sign in in `ALLOWED_EMAILS`.

### 4. Run it locally

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .streamlit/secrets.toml.example .streamlit/secrets.toml   # then fill it in
.venv/bin/streamlit run app.py
```

Set `APP_DEV_MODE = "true"` in secrets to skip Google sign-in while working
locally.

### 5. Deploy

Push to GitHub, then at share.streamlit.io point a new app at `app.py` and
paste the same secrets into **App settings -> Secrets**. Free apps sleep when
idle and wake on the next visit.

### 6. The daily cron

`.github/workflows/discover.yml` runs at 01:30 UTC (07:00 IST). It needs the
same keys under **Settings -> Secrets and variables -> Actions**.

**The repository must stay private.** Workflow logs on a public repo are
readable by anyone and this job touches real user data. Private repos get
2,000 free Actions minutes a month, far more than a daily run needs. Note
that GitHub disables scheduled workflows in repositories with no activity for
60 days - one commit resets that.

## Using it on a phone

The Streamlit app works on a phone: discovery, tailoring, the chat editor and
the downloads all fit a narrow screen. The browser helper is a Chrome
extension, and Chrome on Android does not run extensions, so the phone flow
ends with the tailored file plus copyable answers and a link to the posting.
Submitting through the helper needs a laptop.

## Tests

```bash
.venv/bin/python -m unittest discover -s tests -v
node extension/tests/rules.test.js
.venv/bin/python scripts/check_keys.py      # one live call per configured key
```

`tests/test_core.py` covers redaction, parsing, rendering, scoring and the
fabrication check. `tests/test_ui.py` runs every Streamlit page headlessly
against a fake database, so a broken page fails in CI rather than in front of
a user.

## Layout

```
app.py                  entry point, sign-in gate, navigation
core/
  config.py             settings and the country registry
  auth.py, db.py        sign-in, all Supabase access
  privacy.py            PII redaction (read this one first)
  llm.py                Groq / Cloudflare / Ollama, no vendor SDK
  resume.py, render.py  PDF in, markdown middle, PDF and Word out
  match.py              scoring, ATS keywords, skill gaps
  tailor.py             suggestions, chat, fabrication check
  jobs/                 one module per source, plus dedupe
views/                  one file per Streamlit page
extension/              the Chrome helper (manifest v3)
apps-script/            the Gmail to Calendar script
scripts/discover.py     the cron entry point
scripts/check_keys.py   live check of every key, prints no secrets
supabase/schema.sql     the database, as applied
```

## Limits worth knowing

- Free job APIs are measured in hundreds of calls a month, so discovery is a
  batch job with a call budget (3 titles x 2 locations), not a live search.
- The shared LLM key has a per-user daily cap (`LLM_DAILY_CALL_LIMIT`).
- Supabase free projects pause after a week of inactivity; the daily cron
  keeps this one awake.
- Scanned or image-only PDFs cannot be read. The app says so and asks for a
  normal export rather than guessing.
